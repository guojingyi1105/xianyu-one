# 软件架构与 AI Coding 规范

仅在搭建或优化架构、治理代码结构、单仓/多应用、跨模块改造，或需要 AI Coding 仓库规范时读取。

## 先选复杂度，不先选框架

按证据选择最低足够级别：

1. **小型单体**：按业务功能组织；UI、用例/业务、数据访问和外部集成保持可辨认边界。
2. **模块化单体**：功能域拥有自己的公开入口、内部实现和测试；跨域只经公开契约通信。
3. **工作区/单仓**：多个可独立构建的应用或包共享任务图、依赖图和基础设施。
4. **分布式系统**：只有独立部署、故障隔离、容量差异、合规隔离或团队自治有明确证据时采用。

不要把文件夹数量当作架构。架构至少需要：边界、依赖方向、公开契约、运行时数据流、验证方式和变更理由。

## 仓库地图

编码前用短表记录：

| 区域 | 责任 | 可依赖 | 禁止依赖 | 公开入口 | 验证命令 |
|---|---|---|---|---|---|

同时标出应用入口、核心功能域、共享基础能力、数据存储、外部适配器、生成代码和部署单元。已有仓库先匹配其惯例；除非现状已造成具体缺陷，否则不为追求“标准结构”整体搬家。

## 代码结构规则

- 优先按功能域垂直组织，让一个用户能力的 API、组件、业务规则和测试尽量相邻。
- 共享层只接收已出现至少两个稳定消费者、语义真正一致的能力；不要提前抽象。
- 为每个功能域定义单一公开入口；禁止消费者深入导入内部文件。
- 依赖方向默认从应用编排指向功能域，再指向稳定基础能力；业务核心不反向依赖 UI、数据库 SDK 或供应商实现。
- 外部服务经适配器和明确契约接入；边界处完成校验、错误翻译、超时和可替换测试。
- 禁止跨功能域读写对方私有存储；需要协作时使用公开用例、事件或契约。
- 通过 lint、类型系统、依赖图或架构测试阻止循环依赖、禁用导入和层级倒置。

React/前端项目可采用 `app / features / shared` 的最小结构；功能域内部再按实际需要放置 API、组件、状态和测试。不要无条件复制完整模板。

## AI Coding 指令层

把仓库指令设计为地图和护栏，不写成百科全书：

- 根级 `AGENTS.md` 或等价文件：产品目的、仓库地图、全局边界、安装/运行/测试命令、完成定义和禁止事项。
- 子目录指令：只补充该范围的责任、局部惯例、验证命令和危险区域；与根规则冲突时说明覆盖关系。
- 技术细节放到邻近文档并从指令链接，不把长篇框架教程塞进代理上下文。
- 命令必须可直接运行；路径、包名和测试名来自仓库事实，不猜测。
- 每次代理失误先判断是缺少规则、规则模糊还是未遵守；只补能防止同类错误的最小规则。

推荐的根级结构：

```markdown
# Product and repository map
# Architecture boundaries
# Commands and targeted validation
# Change rules and forbidden areas
# Definition of done
```

## 轻量规格驱动

非平凡功能使用 `意图与验收 → 技术计划 → 任务 → 实现 → 收敛验证`：

1. **意图与验收**：描述用户行为、边界、失败路径和可观察结果，不写实现细节。
2. **技术计划**：映射到现有模块、接口、数据迁移、风险和回滚。
3. **任务**：每项限定文件/模块、依赖、完成条件和验证证据。
4. **实现**：按纵向切片推进，先形成最小闭环。
5. **收敛**：交叉检查规格、计划、任务、代码和测试，处理漂移。

小改动只需要一段“变更契约”：目标、影响文件、不可破坏项、验收与命令。不要为了流程生成无维护价值的文档。

## 变更预算

开始编码前声明：

- 允许修改的模块与公开接口
- 禁止触碰的区域和兼容性约束
- 是否允许新增依赖、共享抽象、数据库迁移或公共 API
- 预计删除、修改、新增的范围
- 必须运行的最小验证集

代理发现需要突破预算时停止扩张，说明证据并更新计划。禁止通过新建平行目录、重复服务或兼容层无限叠加来规避设计问题。

## ADR 与演进式架构

只有难以逆转、跨模块、影响公共契约或显著改变成本/风险的决定才写 ADR。最小字段：

- 状态与日期
- 上下文和驱动力
- 决定
- 被放弃的替代方案
- 正面与负面后果
- 复查或撤销触发器

把关键决定转为适应度检查：依赖边界、循环依赖、包体积、性能预算、迁移兼容、安全或部署约束。优先自动执行；人工检查必须留下可追溯结论。

## 单仓与任务图

只有存在多个应用/包、共享代码、重复 CI 或受影响范围难以判断时才考虑 Nx、Turborepo 或同类工具。

- 明确包图和任务依赖，不依赖隐式执行顺序。
- 缓存任务必须是确定性的；声明真实输入、环境变量和输出。
- 优先运行受影响项目，但发布前保留必要的整体门禁。
- 密钥、时间、网络和机器路径等隐式输入不得污染可复用缓存。
- 工具服务于现有架构，不用工具生成的目录反过来定义业务边界。

## 架构验收

- 新成员或编码代理能从仓库地图找到正确入口。
- 一个功能变更通常落在一个功能域和少量明确边界内。
- 依赖规则可检查，且无新增循环或私有实现穿透。
- 公共 API 小而稳定，外部服务可替换或可测试。
- 规格、ADR、指令与实际代码没有明显漂移。
- 定向测试、架构检查、构建和必要的端到端验证均有证据。

## 来源与取舍

- `github/spec-kit`：吸收规格、计划、任务、实现与收敛的链路；不对小改动强制完整文档流程。
- `agentsmd/agents.md`：吸收可分层的仓库级代理指令、真实命令和作用域规则。
- `nrwl/nx`：吸收项目图、受影响范围、任务依赖与可执行模块边界；不默认引入 Nx。
- `vercel/turborepo`：吸收确定性任务、显式输入输出和缓存纪律；不默认把单应用改成 monorepo。
- `alan2207/bulletproof-react`：吸收功能域组织、共置与单向依赖；不照搬 React 专用目录到其他技术栈。
- `architecture-decision-record/architecture-decision-record`：吸收轻量决策记录、后果与架构适应度检查。
- `github/awesome-copilot`：吸收仓库级与路径级 AI Coding 指令的组织方式；具体规则仍以项目事实为准。

以上项目的代码和文本仍受各自许可证约束；本文件只重新表达可跨技术栈复用的通用方法。
