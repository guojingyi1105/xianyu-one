# 协同前端设计与渲染审查

## 1. 确定设计模式

- 用户主导：逐项提供选择，让用户决定；适合“我来设计”“一步步问我”。
- 方向提案：提出 2–3 个差异明确的方向，用低成本草图或同内容原型比较。
- 直接实现：需求和参考已明确时按约束实现，不重复确认。
- 审查改进：先呈现问题证据和优先级，用户授权后再修改。

## 2. 设计决定单

记录并持续沿用：

- 页面受众、核心任务和首要操作
- 内容层级与页面区块顺序
- 导航与主要流程
- 视觉气质及不希望出现的风格
- 色彩角色、字体策略、间距与密度
- 桌面、移动和窄侧栏行为
- 加载、空、错误、禁用、成功状态
- 可访问性、品牌和现有设计系统约束
- 选用的主组件库、图标库、许可证与需要改造的默认风格

## 3. 实现原则

- 从产品领域、真实内容和用户任务得出视觉方向，避免套用通用 SaaS 模板。
- 先解决层级、流程、布局和状态，再增加装饰。
- 使用语义化结构、清晰标签、键盘焦点、足够对比度和可触控尺寸。
- 保持组件和样式归属清楚，复用现有设计令牌与组件。
- 保持操作命名一致；错误和空状态必须告诉用户下一步。
- 用户提供参考图时区分需要忠实复刻的约束与仅供启发的元素。
- 选择素材前读取 [ui-material-libraries.md](ui-material-libraries.md)，优先复用项目已有体系；新项目只选一个主组件体系。
- 不照搬组件库演示页的默认配色、圆角、阴影和卡片布局；依据设计决定单统一令牌并删除无关装饰。

## 4. 真实渲染循环

1. 启动最小可运行预览，确认资源和控制台无明显错误。
2. 在至少一个桌面和一个移动视口渲染页面；侧栏或嵌入式产品按真实宿主宽度补测。
3. 操作所有变更过的关键控件，并检查默认、悬停、焦点、禁用、加载、错误和完成状态中适用的部分。
4. 截取能代表主流程和关键状态的图片，向用户展示并标注视口、状态和版本。
5. 自查层级、溢出、遮挡、截断、内容真实性、对比度、焦点、响应式和资源加载。
6. 修复可用性缺陷后重新渲染；对审美偏好给用户选择权。
7. 用户确认主要方向后，再进入精修、全量功能或生产集成。

如果运行环境没有浏览器或截图能力，明确说明只能完成静态检查，不得声称已经视觉验收。

## 5. 审查输出

每轮简洁提供：

- 当前设计方向
- 可点击预览或实现文件
- 桌面与移动渲染图
- 已检查的状态
- 需要用户决定的一项问题
- 下一轮修改范围

不要用装饰性效果数量衡量设计质量；以用户能否理解、完成任务和恢复错误为准。
